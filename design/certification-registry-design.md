# Certification registry — design (Phase B, PROPOSED)

**Kit file.** Seeded from `minion-agent-docs` at `dd9fd15`, text preserved. The registry location and examples are Minion-Agent's.

**Status:** design proposal. No data migration is performed by the change that introduces this file.
**Problem:** mutable certification status is duplicated across the normative spec (`**Status: CONTRACT_DRAFT ...**` lines), the parity manifest (`rule:` prefixes, `python:`/`rust:` "candidate pending review" / "not implemented" prose), coordination issues and assurance records. After every closure the spec and manifest need a status-only PR pair: `minion-agent#73` + `minion-agent-docs#172` (WP-13.1), and `minion-agent#93` + `minion-agent-docs#202` (L0506-D001). Stale "not implemented" statements accumulate between syncs.

## 1. Distinguish before changing anything

| Kind | Examples | Stays where it is? |
|---|---|---|
| **Semantic disposition** (part of the traceability contract) | manifest `disposition: adopted / deferred parity / intentional divergence`; `pi:` symbol; `rule:` semantics; `tests:` evidence paths; deferred-parity triggers; intentional-divergence governance | **Yes.** It is normative traceability and is changed only by a semantic/contract change |
| **Implementation location** | manifest `python:` / `rust:` module paths and mechanism notes | **Yes**, as a location/mechanism description, with the status words removed |
| **Transient workflow status** | "CONTRACT_DRAFT", "Implementation candidate, pending independent review", "not implemented; planned", "APPROVED and merged", spec `**Status: ...**` lines | **No.** It moves to the registry |

## 2. Registry

- **Location:** `minion-agent-docs/process/certification-registry.yaml` (docs repo). Status is a process fact about accepted milestones, and the docs repo already owns process/assurance.
- **Authority:** the single source of truth for certification/implementation status per work package and requirement.
- **Shape:**

```yaml
schema_version: 1
work_packages:
  WP-13.1:
    requirements: [TOOL-025, TOOL-026, TOOL-027, TOOL-028, ...]
    coordination_issue: 48
    python:
      status: CERTIFIED            # NOT_IMPLEMENTED | IN_PROGRESS | APPROVED | CERTIFIED | REVALIDATE_REQUIRED
      accepted_code_sha: "<main merge sha>"
      accepted_docs_sha: "<master merge sha>"
      evidence: assurance/layers/13-wp131-python-implementation.md
    rust:
      status: CERTIFIED
      accepted_code_sha: "<sha>"
      evidence: assurance/layers/13-wp131-rust-implementation.md
    cross_language:
      status: CERTIFIED_CLOSED     # NOT_CLOSED | CERTIFIED_CLOSED
      evidence: assurance/layers/13-wp131-...-closure.md
  L0506-D001:
    requirements: [TOOL-041]
    coordination_issue: 88
    python: {status: APPROVED, accepted_code_sha: a993f5d8..., accepted_docs_sha: 6076ad35..., evidence: ...}
    rust: {status: IN_PROGRESS}
    cross_language: {status: NOT_CLOSED}
```

**Status vocabulary** (per language):
- `NOT_IMPLEMENTED`
- `IN_PROGRESS`
- `APPROVED`: shared/Python approved and merged, not yet cross-language
- `CERTIFIED`
- `REVALIDATE_REQUIRED` (§11.8.11)

Cross-language uses `NOT_CLOSED` / `CERTIFIED_CLOSED`.

**Invariants** (validated by `minion-process registry validate`):
- every accepted SHA is reachable from the default branch;
- `CERTIFIED` requires an evidence path that exists;
- `CERTIFIED_CLOSED` requires both languages `CERTIFIED`;
- every requirement ID exists in the manifest;
- no requirement belongs to two WPs with conflicting statuses.

## 3. Derived views instead of hand-written status

- **Spec.** Remove the `**Status: ...**` lines from `spec/**` during migration. Where a reader needs status, the spec says *"Certification status: see `process/certification-registry.yaml` (`<WP id>`)"*. That line is stable text and never needs a status-only edit.
- **Manifest.** `python:` / `rust:` keep the module/mechanism location, and the status words ("pending review", "not implemented; planned", "APPROVED and merged") are dropped. The `rule:` field loses its `CONTRACT_DRAFT (...)` prefix: that prefix is status, not semantics. Manifest validation gains a cross-check that each row's requirement appears in the registry with a consistent disposition, e.g. a `deferred parity` row is not registered `CERTIFIED`.
- **Human-readable status tables** (layer summaries, README status) are generated by `minion-process registry render`, or validated against the registry in CI. They are never hand-maintained.

## 4. Update rule

A status change is part of the workflow transition that causes it:
- **merge** of an approved candidate → `APPROVED`, with the accepted SHAs;
- **certification** → `CERTIFIED`;
- **closure** → `CERTIFIED_CLOSED`.

Under standing delegation #75 these are routine transitions: Claude updates the registry in the same docs PR as the assurance record, or in the merge's follow-up commit. There is no separate status-only PR pair.

## 5. Migration (incremental, after independent approval)

1. Create the registry, seeded from current default-branch assurance records. Each seeded row cites the assurance record it came from.
2. Add `minion-process registry validate`, and run it in the docs and code gates.
3. Remove the spec `**Status:**` lines and the manifest status words in one reviewed PR pair, the last status-only pair. It is a documentary change validated against the registry.
4. From then on, status changes touch only the registry.

**Risks.** Existing parsers of manifest prose (the manifest validator reads `python:`/`rust:` as strings only) are unaffected by removing words. The migration PR must show `test_manifest_validation` green and must not change any `rule:` semantics beyond removing the status prefix.
